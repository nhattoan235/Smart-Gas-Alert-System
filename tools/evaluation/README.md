# Offline trace evaluation

`evaluate_trace.py` computes sample-level confusion metrics and optional episode latency from a labeled CSV trace. It does not connect to MQTT, Wokwi, the dashboard database, or a physical sensor.

Run it with:

```powershell
python tools/evaluation/evaluate_trace.py path\to\trace.csv
```

The input must have these columns:

| Column | Meaning |
|---|---|
| `source_type` | Exactly one of `synthetic`, `wokwi`, `integration`, `physical`; the author supplied label is echoed in output. |
| `run_id`, `scenario`, `device_id`, `gas` | Trace grouping. `gas` is `LPG` or `CO`. |
| `truth_hazard` | Ground-truth label for this sample: `true`/`false` or `1`/`0`. |
| `state` | Detector state: `WARMUP`, `SAFE`, `WATCH`, `WARNING`, `DANGER`, `FAULT`, or `OFFLINE`. |
| `valid` | Whether this detector sample is valid: `true`/`false` or `1`/`0`. |

Optional columns are `sample_time_ms`, `truth_episode_id`, `hazard_start_ms`, and `first_alarm_ms`. `sample_time_ms` is a non-negative monotonic sample timestamp. Rows without it do not enter the confusion matrix. The three episode columns are used for latency only when all needed markers are present. Repeat `hazard_start_ms` and `first_alarm_ms` on one or more positive-truth rows for the same episode, using identical values. Conflicting values are rejected. An alarm timestamp before hazard onset is counted as a pre-alert and is not reported as negative detection latency.

`WATCH`, `WARNING`, and `DANGER` count as detector-positive. Confusion metrics include only timestamped rows where `valid=true` and the state is one of `SAFE`, `WATCH`, `WARNING`, or `DANGER`. `FAULT`, `WARMUP`, `OFFLINE`, invalid, and untimestamped rows are kept out of TP/FP/TN/FN and are shown as exclusions. Their counts are highlighted in `availability_exclusions`; excluding sensor-availability failures can make a gas-hazard miss rate look lower. Rates are fractions from 0 to 1: false-alarm rate is `FP / (FP + TN)`, miss rate is `FN / (TP + FN)`. A zero denominator is JSON `null`.

Episode latency is calculated only as `first_alarm_ms - hazard_start_ms` for a matching explicit `truth_episode_id`. The dataset author must define what `first_alarm_ms` measures. Unless the data notes say otherwise, interpret it as the first detector alarm-state assertion time; it is not a measured physical pin edge. If the episode ID or either timestamp marker is absent, latency is `NA` for that episode; the tool does not infer real onset or alarm times from dashboard receipt timestamps. It does not interpolate between samples. P50 is the median measured episode delay. P95 uses the nearest-rank rule but is emitted as `NA` below 20 measured episodes; low-count quantiles are not presented as stable performance estimates.

## Smoke fixture

`fixtures/metric-smoke.csv` is deliberately hand-authored arithmetic test data. Its detector states are not generated by firmware and it is not evidence about detection performance. The unit test checks the known TP/FP/TN/FN arithmetic and a 200 ms explicit marker difference. Do not present its output as Wokwi, integration, or physical-sensor results.

The source label separates evidence classes, but the tool cannot verify that label. A synthetic result remains synthetic; a dashboard receipt timestamp is not a sensor-onset timestamp. Physical gas measurements require a documented sensor setup, calibration, and independently timestamped scenario ground truth.
